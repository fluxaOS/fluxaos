## Open Items Resolved for This Plan

Per AGENT_BEHAVIOR.md autonomy and the no-invented-thresholds rule:

1. **Cleanup thresholds.** Not picked. The plan ships with **no defaults** — env vars are required at scheduler startup. If unset, the scheduler emits a single warning and does not start. The user picks values once by setting them in `.env.local`; acceptance criteria include a verification that the scheduler refuses to start without them.
2. **Commit-message format / PR-body template.** Shaped as functions with the structure below; exact prose is code, not spec, so reviewable at PR time rather than plan time.
   - Commit message: `<stage-name>(<issue-number>): <issue-title>` — body contains the issue URL and run URL
   - PR title: `<issue-title> (#<issue-number>)`
   - PR body: sections `## Issue`, `## Pipeline Run`, `## Stages`, `## Generated by fluxaOS`
3. **Branch-name convention.** `fluxaos/issue-<number>-<run-id-short>` — issue number + 8-char run id suffix. The run-id suffix prevents collisions when the same issue retries after a rework cycle (`issue-42` retry would fail `git branch` without it). User can override per-project later via a new `project.branchNameTemplate` column — **not adding in this plan**, deferred until a second run against the same issue surfaces the need.
4. **Default `baseBranch`.** New `project.default_branch` column defaults to `'main'`. Post-alpha detection via `gh repo view` is a PATH not taken here.
5. **Octokit version.** `@octokit/rest` latest stable at install time (a single add). No transitive Octokit in current deps (verified via `grep octokit package.json` — empty). Pin to the minor at install.
6. **Node.js minimum git version.** Shell-out uses `git worktree add --no-track` + partial-clone flags; requires git 2.30+. Documented in R-POLISH's README pass; not enforced at this phase.
7. **Orchestrator crash-recovery.** Out of scope for this plan; R-DAEMON owns it. The `acquire()` upsert-repair semantics make it possible; the plan doesn't exercise it.
8. **Artifacts directory.** Stubbed in the isolation provider (`acquire()` returns an optional `artifactsPath` field that R-ARTIFACTS fills in). Plan wires up the field but leaves it empty. No orchestrator consumer for alpha.

### Wave 3 — Isolation provider (DB-aware)

**T6. `src/adapters/git/worktree-isolation-provider.ts`**

Implements `IsolationProvider` using T3/T4/T5 helpers + Drizzle.

- `acquire(params)`:
  1. Resolve paths via `path-resolver`
  2. Start a Drizzle transaction
  3. Query `isolation_environment` WHERE (projectId, runId, status='active') — if row exists:
     - If `worktreeExists(row.workingPath)` → return existing (no-op repair)
     - Else → mark row `inactive`, continue to create
  4. Create the worktree on disk via `createWorktree`
  5. Copy configured gitignored files via `copyConfiguredFiles` (pull list from `project.worktree_copy_files`)
  6. Insert new `isolation_environment` row with `status='active'`
  7. Commit transaction
  8. Return `IsolationEnvironment` domain object

- `release(envId, { force })`:
  1. Load env row
  2. If `!force && hasUncommittedChanges(env.workingPath)` → throw `UncommittedChangesError`
  3. `removeWorktree(repoPath, env.workingPath, { force })`
  4. Update row `status='inactive'`
  5. Idempotent: if row already inactive or worktree already gone, succeed silently

- `findActiveByRun(projectId, runId)` — direct DB read
- `listActiveByProject(projectId)` — direct DB read

Integration test: full lifecycle (acquire→release), repair after manual worktree deletion, concurrent acquire race (two parallel calls → same row returned), uncommitted-changes guard.

### Wave 4 — Cleanup service

**T7. `src/core/cleanup/cleanup-service.ts`**

- `onPrClosed(prNumber, { merged }): Promise<void>` — looks up env by branch via `issue_pull_request` join → `isolation_environment`; calls `removeEnvironment` with `deleteRemoteBranch: merged`
- `removeEnvironment(envId, { force }): Promise<RemoveEnvironmentResult>`
- `runScheduledSweep(): Promise<CleanupReport>` — finds candidates via `listActiveByProject` × all projects; applies safety checks; releases safe ones; emits report
- `cleanupToMakeRoom({ requiredBytes? }): Promise<CleanupReport>` — sorts by age, reaps oldest safe until quota met
- `listBreakdown({ projectId }): Promise<BreakdownReport>` — for Mission Control UI (post-alpha consumer, shipped now because the query is trivial)
- Internal `isSafeToRemove(env)`:
  - `hasUncommittedChanges(env.workingPath)` → `{ safe: false, reason: 'uncommitted' }`
  - `isBranchMerged(repoPath, env.branchName, defaultBranch)` → `{ safe: true, reason: 'merged' }` (reap)
  - `openPrExists(env.branchName)` → `{ safe: false, reason: 'open-pr' }`
  - `ageDays(env.createdAt) > FLUXAOS_CLEANUP_STALE_DAYS` → `{ safe: true, reason: 'stale' }`
  - otherwise → `{ safe: false, reason: 'active-but-not-stale' }`

Integration tests: one per trigger + one per safety-check branch.

### Wave 6 — Deploy bridge + orchestrator integration

**T13. `src/core/deploy/deploy-bridge.ts`**

Factory function `createDeployBridge({ db, registry, logger })`. Returns an object with `deploy(runId): Promise<DeployResult>`.

`deploy(runId)`:
1. Load the `pipeline_run` row + the `issue` row + the `project` row
2. Find the active `isolation_environment` for this run
3. If none → throw (bug: deploy called without an env)
4. `commitAll(env.workingPath, buildCommitMessage({ issue, run, project }))` — if `{ noChanges: true }`, log and skip the push/PR steps (alpha: no-op commits don't open PRs)
5. `push(env.workingPath, env.branchName, { setUpstream: true })`
6. `git.createPullRequest({ repo: project.repoUrl, title, body, headBranch: env.branchName, baseBranch: project.default_branch })` — using registry git provider
7. Insert `issue_branch` row (issueId, repo, branchName=env.branchName, isPrimary=true, createdBy='fluxaos')
8. Insert `issue_pull_request` row with all fields from the PR response
9. Call `issueService.transitionTo(issueId, reviewStateId, currentVersion)` — advances issue to `review` state
10. `isolation.release(env.id)` — worktree gone, branch stays (PR owns it)
11. Return `{ pr, branchRowId, prRowId }`

All the DB writes in steps 7-9 happen inside a **single Drizzle transaction**. The external calls (push + createPR) happen BEFORE the transaction; the transaction only persists their results. If push fails or createPR fails, no DB side-effects. If the transaction fails after push+createPR succeed, we have a branch + PR on GitHub without a DB record — logged loudly, manually recoverable, acceptable for alpha.

Integration test (no creds needed): mocks the registry `git` provider with a fake; asserts DB rows and state transition occur; asserts `release` is called.

**T14. Orchestrator integration — `stage-runner.ts`**

**T16. Orchestrator integration — `event-orchestrator.ts` / pipeline terminal hook**

Edit the pipeline-terminal-completion hook to invoke the deploy bridge:
- When a `pipeline_run` transitions to terminal `completed` status and its last stage was implement/deploy (i.e., produced code), call `deployBridge.deploy(pipelineRunId)`
- On `failed` status, call `isolation.release(envId, { force: false })` — if uncommitted changes exist, it stays for debugging (user deletes manually or cleanup-service reaps as stale)
- Grep for the existing terminal-state handler to find the right file — may be `event-orchestrator.ts` or `pipeline-run-service.ts`; plan notes this is a read-first task

**Decision: "produced code" detection.** The deploy bridge should only fire when the pipeline actually wrote changes. Simplest signal: `commitAll` returning `{ noChanges: true }` skips the push+PR path (already handled in T13 step 4). That's the cleanest place — **deploy always gets called on terminal success; the bridge itself no-ops when there's nothing to ship**. No special-casing pipeline shape required.

## Commit / Merge Discipline

- One commit per task (T1..T20), unless a task produces ≤10 lines (then bundled with a neighbor).
- Branch: `feat/r-runtime` (this plan lives on `plan/r-runtime`; execution will create `feat/r-runtime` off current main).
- Task ordering is not the commit ordering if earlier tasks block later tasks. Wave boundaries are commit checkpoints — run lint + tsc between waves.
- No `--no-verify` commits. No amend of pushed commits.
- PR opens at end of Wave 4 for schema/ports/cleanup review, then work continues on the same branch through Waves 5-8. Alternative: one final PR at Wave 8. **Decision: one final PR.** Intermediate PRs on a multi-week phase create merge-order problems and pull review attention thin. Per the R-REM-W2 / R-REM-W3-a precedent: one phase, one PR.
- Merge requires:
  - All Wave-8 verification green
  - Human UI sign-off recorded in PR body
  - CI `check` either green or the remaining redness confined to DEF-018 and reported in the PR

## Risks and Mitigations

All risks carry over from the spec. Plan-specific risks:

**R-PLAN-1 — Migration 0007 conflicts with in-flight schema work.** No other branches touch schema right now (verified on `main` at `ece3ee7`). If a parallel schema PR lands before R-RUNTIME merges, rebase + regenerate drizzle migration.

**R-PLAN-2 — `@octokit/rest` transitive bloat.** Octokit's full `@octokit/rest` package pulls many plugins. **Mitigation:** if `npm ls @octokit/rest` reveals >20 transitive deps, switch to `@octokit/core` + hand-roll the 2 endpoints we use. Decision made at T9 install time, not before.

**R-PLAN-3 — `isolation.acquire` blocking stage-runner in a way that serializes runs that could parallelize.** Acquire is per-`(project, run)`, not global; different runs acquire independent rows. No serialization risk. Flagged here only to preempt the reviewer's question.

**R-PLAN-4 — Worktree cleanup races on Windows/WSL.** fluxaOS runs on Linux (homelab); not concerned. Flagged for R-POLISH if cross-platform matters.

**R-PLAN-5 — Octokit rate-limit with a PAT.** PAT = 5000 requests/hour authenticated. Alpha volume is one PR per successful run; rate limits don't bite. **No mitigation needed.**

## What Changes After This Plan Merges

- **Engine runs in isolated worktrees.** Every pipeline run gets its own git checkout of the target repo on a dedicated branch. No more "worker wanders into fluxaOS source tree" bugs.
- **Loop closes.** File issue → pipeline runs → PR opens → issue in `review`. The full alpha definition-of-done shape is exercised.
- **`IssueProvider` port is gone.** The retire-dead-ports precedent continues.
- **GitHub becomes a first-class integration.** Future forge adapters (GitLab, Gitea) plug into the same `GitProvider` port.

**What does NOT change:**
- The subprocess driver (stage-executor) is untouched. It still gets a `cwd` and executes the configured binary. R-RUNTIME changes what `cwd` points at.
- The skill/persona/context materialization is unchanged in content — just relocated into the worktree instead of a tmp dir.
- The pipeline DAG, gate engine, state machine — all untouched.
- The web UI — untouched in this phase (Mission Control UI to read isolation state is R-MISSION-CONTROL).

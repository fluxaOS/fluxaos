# FLX-239 Stage 2 — Seed Rewrite Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rewrite `src/scripts/db/seed.ts` to use the new tenancy schema (customer → org → team → user → project), add `team_member` and `project_member` junction rows, fix all catalog-feature inserts to use `kind='catalog'`/`kind='org'`/`kind='project'` with explicit NULL scope columns, update `tests/verify/seed-check.ts` with auth-identity, denormalization, and tenancy-shape invariants, and get seed.ts TypeScript-clean.

**Architecture:** Stage 1 added `customer`, `team`, `teamMember`, and `projectMember` tables, dropped `project.user_id` and `skill.scope`/`persona.scope` (among other column drops), and **reset all catalog-feature rows (persona/skill/brand/provider/driver/routing_profile) to `kind='catalog'` with NULL scope FKs** via Phase 12 of the migration. The seed currently uses dropped columns, causing 4 TypeScript errors, and must also handle the UAT case where existing rows have been reset to `kind='catalog'` but the seed wants them at `kind='org'`/`kind='project'`. Idempotency is therefore both a TS-correctness issue and a runtime row-state issue.

**Idempotency strategy (applies project-wide):** Every entity insert in this plan uses the **check-then-insert-or-update** pattern (mirrors `pipeline` upsert at `src/scripts/db/seed.ts:117–134`). No `.onConflictDoNothing()` calls are used for tables without a matching unique constraint, because Postgres has nothing to conflict on and `gen_random_uuid()` PKs never collide — so the call becomes an unconditional INSERT that produces duplicate rows on re-seed.

**Tech Stack:** TypeScript 5, Drizzle ORM, Supabase Cloud (Postgres), `@supabase/supabase-js` admin client for auth-identity assertion.

### 2g: Fix catalog-feature inserts (skill, persona, brand, provider, routingProfile)

Stage 1 dropped the `scope` column from `skill` and `persona`. It also dropped `orgId NOT NULL` from `provider`, `routingProfile`, and `brand` (those columns are now nullable waterfall scope columns).

**UAT idempotency consideration:** Stage 1's Phase 12 migration UPDATEs every existing row in `persona`, `skill`, `brand`, `provider`, `driver`, `routing_profile` to `kind='catalog'` with all four scope FKs NULL. On a freshly-nuked dev DB, the seed inserts fresh rows so this is irrelevant. On UAT (which persists across deploys per CLAUDE.md), pre-existing rows landed at `kind='catalog'`/NULL-scope after Stage 1 migration. The seed must therefore use a **check-then-update-or-insert** pattern that promotes existing reset rows to the correct kind/scope, not `.onConflictDoNothing()` which would silently leave them in the wrong state.

The catalog-feature rows split into three kinds in this seed:

| Entity | Kind | Scope columns | Pattern |
|---|---|---|---|
| `skill` (5 rows: research/implement/review/rework/deploy) | `catalog` | all NULL | check-by-name + isNull-on-all-scope-cols → INSERT-or-UPDATE |
| `driver` (claude-code, openai-codex) | `catalog` | all NULL | already uses `onConflictDoNothing({ target: driver.slug })` — `driver.slug` IS uniquely indexed, so the conflict target is real and the existing code stays. Add explicit `kind: 'catalog'` + NULL scope cols for clarity; the migration's Phase 12 reset already left existing rows in this state. |
| `provider`, `routingProfile`, `brand` | `org` | orgId set, others NULL | check-then-INSERT-or-UPDATE (no unique constraint exists for `(org_id, name)` post-migration; partial indexes exist but Drizzle doesn't currently support `WHERE` clauses on conflict targets) |
| `persona` (5 rows, one per stage) | `project` | projectId set, others NULL | check-then-INSERT-or-UPDATE (existing block already check-then-inserts; add UPDATE branch to handle reset rows) |

## What This Session Did

### Task 1: Extended `SkillSignal` Interface

**File:** `src/core/orchestrator/signal-parser.ts`

Added `reason?: string` to `SkillSignal` interface. Typed `meta` from `Record<string, unknown>` to `{ targetState?: string; question?: string; [key: string]: unknown }`. `parseSignalObject()` now extracts `reason` from the signal data object alongside existing fields.

Added 3 new tests to `src/__tests__/integration/signal-parser.test.ts`:
- Signal with `reason: 'already_complete'` and `meta.targetState` — verified parsed
- Signal with `reason: 'needs_human'` and `meta.question` — verified parsed
- Signal with no `reason` field — verified parses without error, `reason` is undefined

Total parser tests: 15 (12 existing + 3 new).

### Task 2: Wired `hold` Verdict Handling in `manual-run.ts`

**File:** `src/core/orchestrator/manual-run.ts`

After `executeStageRun()` completes, if `skillSignal === 'hold'` and there's an `issueId`:

**For `hold/already_complete`:**
1. Fetches issue row from DB (to get `projectId` and `version`)
2. Looks up target state by key via `issueService.getStateByKey(projectId, targetStateKey)`
3. Calls `issueService.stateOverride(issueId, targetState.id, version, 'orchestrator')`
4. Writes `state_changed` issue event with reason and target state

**For `hold/needs_human` (or unknown reason):**
1. Fetches issue row
2. Resolves blocked status via `issueService.getStatusIdByConfigKey(projectId, 'issues.status.on_blocked_key')`
3. Calls `issueService.updateStatus(issueId, blockedStatusId, 'orchestrator', question)`
4. Writes issue event with reason and question

New imports: `createIssueService`, `GATE_VERDICT`, `issue` schema.

### Task 3: Wired `hold` Verdict Handling in `event-orchestrator.ts`

**File:** `src/core/orchestrator/event-orchestrator.ts`

Same logic as Task 2, but in the `applyVerdict()` function. `applyVerdict()` now takes two additional optional parameters:

```typescript
async function applyVerdict(
  run, stage, sRun, verdict,
  signalReason?: string | null,    // NEW
  signalMeta?: Record<string, unknown> | null,  // NEW
)
```

The `hold` branch now checks `signalReason` and either:
- Calls `stateOverride` for `already_complete`
- Sets status to `blocked` for `needs_human`

Call sites updated to pass `result.skillSignalReason` and `result.skillMetadata`.

### Task 4: Gate Results Always Written

**Files:** `manual-run.ts`, `event-orchestrator.ts`

Previously, `gateService.evaluateStageGate()` was only called when `exitCode === 0 && gateMode === 'rules'`. Now called unconditionally after every stage run completion.

The gate engine already handles all modes:
- `auto`/`skip` → returns `{ verdict: 'proceed', reason: 'gate mode: auto' }`
- `hold`/`manual` → returns `{ verdict: 'hold', reason: 'gate mode: hold — manual release required' }`
- `rules` → evaluates rules and returns verdict

This means `stage_gate_result` is now written for every stage run. The Gates tab in the run detail modal will show results for every run regardless of mode or outcome.

### Task 5: Rewrote Skill Prompt Templates for Pipeline Execution

**File:** `src/core/db/seed.ts`

- What NOT to do (no slash commands, no CLI tools)

Removed `readFileSync` and `join` imports (no longer needed). Also removed unused `sql` import from drizzle-orm.

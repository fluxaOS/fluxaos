### 6. Designed `hold` Verdict Semantics

Discovered that `hold` needs two distinct meanings. Designed the protocol:

**`hold/already_complete`** — skill assessed the issue and found the work is already done. The issue's current state is wrong (e.g. stuck in `research` when impl+review+deploy are done).

Signal shape:
```json
{"flux:signal": {"verdict": "hold", "reason": "already_complete", "summary": "Health endpoint already fully implemented", "meta": {"targetState": "complete"}}}
```

Orchestrator action: call `issueService.stateOverride(issueId, targetStateId, version, 'orchestrator')` — this bypasses the transition table (which is for human-initiated moves only) and writes directly, recording `override: true` in the audit trail.

**`hold/needs_human`** — skill is blocked and cannot proceed without human input. Expected to be very rare once the system is mature (skills should be written to handle ambiguity autonomously).

Signal shape:
```json
{"flux:signal": {"verdict": "hold", "reason": "needs_human", "summary": "Cannot determine auth strategy", "meta": {"question": "Should this use OAuth or API keys?"}}}
```

Orchestrator action: set issue status to `blocked` — no state change, surfaces to user for intervention.

**Key design decision:** No new `issue_transition` rows are needed for signal-driven jumps (e.g. `research → complete`). The transition table enforces the human workflow only. `stateOverride()` is the privileged path for automated moves, same as a human clicking "change state" in the UI.

`issueService.stateOverride()` already exists at `src/core/services/issue.ts:460`. It:
- Validates the target state exists
- Does NOT check the transition table
- Updates `isClosed` and `closedAt` if target state is terminal
- Uses optimistic concurrency (`WHERE version = $expected`)
- Records a `state_changed` event with `override: true`

### Task 2: Wire `hold` Verdict Handling in `manual-run.ts`

**File:** `src/core/orchestrator/manual-run.ts`

Currently `manual-run.ts` calls `gateService.evaluateStageGate()` only when `gateMode === 'rules'` AND `exitCode === 0`. The skill signal verdict is never acted on for `hold`.

**What needs to happen after a stage run completes with a skill signal:**

1. If `skillSignal === 'hold'` and `signal.reason === 'already_complete'` and `signal.meta.targetState`:
   - Look up the target state ID by key from the `issue_state` table for the issue's project
   - Call `issueService.stateOverride(issueId, targetStateId, issue.version, 'orchestrator')`
   - Write an issue event: `ISSUE_EVENT_TYPE.state_changed` with reason and targetState in payload

2. If `skillSignal === 'hold'` and `reason === 'needs_human'` (or reason is absent/unknown):
   - Look up the `blocked` status ID from `issue_status` table for the issue's project
   - Call `issueService.updateStatus(issueId, blockedStatusId, ...)` — check the signature in `src/core/services/issue.ts`
   - Write an issue event noting the block reason/question

3. `issueService` is not currently imported in `manual-run.ts` — you'll need to instantiate it via `createIssueService(db)` (check `src/core/services/issue.ts` for the factory function name).

**Note on optimistic concurrency:** `stateOverride()` requires `version`. You'll need to fetch the issue's current version from the DB before calling it. The issue ID is in `result.issueId` from `executeStageRun()`.

### Task 5: Rewrite Skill Prompt Templates for Pipeline Execution

**Root cause of token waste:** The seed reads skill content from `.claude/skills/<name>/SKILL.md` at seed time (`src/core/db/seed.ts:224`). These files are full interactive pipeline skill files containing:
- Workflow instructions referencing `pat pipeline exit`, `flu` CLI, worktrees
- Instructions to use slash commands
- Instructions to run `flu issue list`, read multiple config files, etc.

When Claude runs in `--print` mode inside an isolated workspace, none of this context exists. Claude tries to invoke slash commands (fails), runs CLI tools that aren't available, and does excessive file reads.

**What the DB skill `promptTemplate` should contain instead:**

A lean, self-contained prompt that tells Claude exactly what to do in the pipeline context:

```
You are running as a pipeline agent in headless mode. You have two files available:
- CLAUDE.md — your instructions and skill definition
- context.md — the issue you are working on

Read both files. Assess the issue. Do the work described in CLAUDE.md for this issue.
When complete, emit your result as a flux:signal on a single line:
echo '{"flux:signal": {"verdict": "proceed", "summary": "brief description of what was done"}}'

If the issue is already complete or in the wrong state, emit:
echo '{"flux:signal": {"verdict": "hold", "reason": "already_complete", "summary": "explanation", "meta": {"targetState": "<state>"}}}'

If you cannot proceed without human input, emit:
echo '{"flux:signal": {"verdict": "hold", "reason": "needs_human", "summary": "explanation", "meta": {"question": "specific question"}}}'

Do not ask questions. Do not use slash commands. Do not run CLI tools beyond what the task requires.
```

**Implementation options:**
1. Add a `pipeline-prompt.md` alongside each `SKILL.md` in `.claude/skills/<name>/` — seed reads this instead
2. Store the lean prompt directly in seed code (simpler, no extra files)
3. Keep loading from `SKILL.md` but add a `## Pipeline Prompt` section that the seed extracts

Option 2 (inline in seed) is simplest for now. The skill-specific content (what "research" means vs "implement") lives in `CLAUDE.md` written by the materializer — the prompt template just needs to tell Claude how to behave in the pipeline context.

**Verify after implementing:** Run a stage from the UI. Output should be clean — no slash command attempts, no CLI tool calls except what the task genuinely requires.

## Things That Will Bite You

1. **Always nuke+seed after changing seed.ts** — the seed uses `onConflictDoNothing()` so re-running without nuke won't pick up changes to existing rows.

2. **`--output-format stream-json` requires `-p`** — without `-p`, Claude runs interactively and never terminates. The seed now includes `-p` but double-check if behavior seems wrong.

3. **`stateOverride()` requires current version** — fetch the issue from the DB immediately before calling it to get the latest version number. Stale version = `VERSION_CONFLICT` error.

4. **Gate results are per stage run, not per pipeline run** — `GateResultsPanel` takes a `stageRunId`. The Gates tab is only populated for the selected stage, not the whole pipeline run.

5. **`manual-run.ts` is fire-and-forget** — it runs in the background after the tRPC mutation returns. Errors are caught and logged but not surfaced to the UI directly — check server logs if behavior seems wrong.

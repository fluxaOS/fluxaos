# R5.5 — Skill-to-Orchestrator IPC Protocol Design

**Date:** 2026-04-13
**Status:** Approved
**Depends on:** R5-V (PR #20, merged)
**Blocked by:** Nothing

---

## Problem

Skills run as subprocesses via `claude --print`. The orchestrator (systemd daemon) is the single DB writer. Skills cannot write to the database directly. After R5-V, the only completion signal is the process exit code — 0 means completed, non-zero means failed. This is insufficient:

- Exit code 0 means "ran without crashing", not "advance to next stage"
- The skill may find work is already done, needs rework, or is blocked
- The skill owns the outcome decision — the orchestrator only manages execution lifecycle
- There is no mechanism for skills to report metadata (summary, cost, tokens, PR #, branch)
- Output arrives as a batch at process exit, not streamed in real-time
- All output is parsed as `raw` text because `claude --print` doesn't emit structured JSON

## Decision Record

Alternatives considered and rejected during brainstorming:

| Option | Why rejected |
|--------|-------------|
| **tmux sessions** (PAT's approach) | Solves problems from interactive mode that `--print` doesn't have. Adds session management complexity and crash recovery bugs |
| **Redis pub/sub** | Claude can't publish to Redis — would need MCP tool, same complexity as option below |
| **MCP tool / local API** | Unnecessary infrastructure. Need to run a server, handle auth, manage lifecycle, handle skill crashes before calling it |
| **Post-hoc output parsing** | Fragile. Inferring intent from natural language ("I completed the work" vs "the work was already done") is unreliable |
| **Adopt OpenHands** | Solves a different problem (single-task agent execution). No multi-stage pipelines, no gates, no per-stage config. Python monolith, can't embed in TypeScript |

**Chosen approach:** Structured JSON signal lines in stdout, parsed by the stage-runner in real-time.

---

## Design

### 1. Signal Protocol

Skills emit a single structured JSON line to stdout at any point during execution:

```json
{"flux:signal": {"verdict": "proceed", "summary": "Implemented health endpoint with build metadata"}}
```

**Rules:**

- Recognized by the `flux:` namespace prefix — no collision with harness JSON output
- Last signal wins — if the skill emits multiple, the final one is authoritative
- `verdict` is required — uses existing `GateVerdict` values: `proceed`, `hold`, `rework`, `abort`
- Optional top-level fields: `summary` (string), `cost_usd` (number), `tokens_in` (integer), `tokens_out` (integer)
- Optional `meta` object: open-ended key/value map for skill-specific data (e.g., `{"pr_number": 42, "branch": "feat/health"}`)
- `summary` and cost/token fields write to `skill_metadata` and the existing `costUsd`/`tokensIn`/`tokensOut` columns respectively. `meta` merges into `skill_metadata`.
- Skills **must** emit a `flux:signal` line. If no signal is found in stdout after process exit, the stage run fails with error: "no skill signal emitted"

**The skill signal is not authoritative** — it is data that gate rules can reference, like any other metric. The gate engine remains the single decision authority.

### 2. Schema Changes

#### `stage_run` — four new columns

| Column | Type | Purpose |
|--------|------|---------|
| `skill_signal` | text, not null | Verdict from the skill (`proceed` / `hold` / `rework` / `abort`) |
| `skill_metadata` | jsonb | Summary, PR #, branch, and any other skill-reported data |
| `trigger` | text, not null | `'manual'` or `'automated'` — who initiated the run |
| `error_message` | text | First error, for quick access without scanning events |

Existing columns already cover: `model`, `harness`, `harnessId`, `skillId`, `provider`, `exitCode`, `costUsd`, `tokensIn`, `tokensOut`, `startedAt`, `completedAt`, `pid`, `attempt`, `status`.

#### `harness_catalog` — one new column

| Column | Type | Purpose |
|--------|------|---------|
| `output_format` | text, not null | Output mode for this harness (e.g., `'stream-json'`, `'text'`) |

The command builder reads this to set the correct output flag. Different harnesses emit different formats. Missing `output_format` fails fast — no silent defaults.

### 3. Real-Time Output Streaming

**Current problem:** `claude --print` outputs plain text all at once when the process exits. LiveOutput shows nothing until the run completes.

**Fix:** Switch Claude's harness config to streaming JSON output (`--output-format stream-json`). Each JSON event arrives as it happens.

**Stage-runner stdout handler flow:**

1. Line arrives from subprocess stdout
2. Is it `{"flux:signal": ...}`? → Parse and hold in memory, overwriting any previous signal. Do not store as an event.
3. Otherwise → parse via output parser, write to DB immediately as an `output` event

No post-exit batch write. Events arrive in the DB in real-time. Supabase Realtime delivers them to LiveOutput immediately.

### 4. Output Parser per Harness

The output parser currently assumes Claude's streaming JSON format. With `output_format` on the harness catalog, parsing becomes config-driven:

- The stage-runner selects the parser based on `output_format` from the harness config
- All parsers produce the same `TranscriptEntry` types: `text`, `tool_call`, `tool_result`, `result`, `system`, `raw`
- The UI renders from `TranscriptEntry` — it doesn't know which harness produced them

**Parsers to implement:**

| Format | Description |
|--------|-------------|
| `stream-json` | Claude's streaming JSON (`assistant`, `user`, `result`, `system` event types). The existing `output-parser.ts` already handles this. |
| `text` | Plain text harnesses. Each non-empty line becomes a `text` entry. This is a first-class format, not a fallback — chosen explicitly in harness config. |

Future harnesses add their own parsers.

### 5. Integration Points

#### Manual-run (`manual-run.ts`)

- Passes `trigger: 'manual'` to stage-runner
- After completion, skill signal is stored on the stage run
- Admin sees the signal in the UI and decides next action

#### Event-orchestrator (`event-orchestrator.ts`)

- Passes `trigger: 'automated'`
- After completion, reads `skill_signal` from the stage run
- Feeds it to gate evaluation as a field that rules can reference
- Gate engine produces the final verdict — skill signal has no special authority

#### Gate rules

Gate rules can reference `skill_signal` as a field in rule conditions:

- "If `skill_signal` = `rework`, verdict = `rework`"
- "If `skill_signal` = `hold`, verdict = `hold`"
- Or ignore it entirely — the user controls gate configuration

### 6. No Fallbacks

- Skills **must** emit a `flux:signal` line. No signal → stage run fails with `error_message: "no skill signal emitted"`
- Harness catalog **must** have `output_format` set. Command builder fails fast if missing.
- The `text` output format is not a fallback — it's a first-class format for harnesses that genuinely output plain text. Chosen explicitly in config, not inferred.
- No silent defaults. No graceful degradation. Misconfiguration surfaces immediately.

---

## Out of Scope

- Heartbeat / keepalive protocol — subprocess timeout is sufficient
- Bidirectional communication (orchestrator → skill mid-execution)
- RealtimeProvider adapter implementation (separate deferred fix)
- LiveOutput UI redesign (structured data enables it; the UI work belongs to R-UI)

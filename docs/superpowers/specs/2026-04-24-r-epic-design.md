# R-EPIC — Epic / Child-Issue Hierarchy

**Phase:** R-EPIC
**Status:** SPEC
**Created:** 2026-04-24
**Author:** Claude Opus 4.7 (1M)
**Depends on:** R-ARTIFACTS (Done) — none on code path, only on "alpha gates pass"

## 1. Problem

fluxaOS's issue model is flat. Every issue is a work item. There is no way to express "this issue is a container for smaller pieces of work" — no epic → story relationship, no way to decompose a large task into independently-shippable children, no way for the orchestrator to tell "this issue is itself work to run" from "this issue is a parent that will be Done when its children are Done."

Alpha operators — in practice, the user driving chain journeys against the sandbox — have already felt this: when the deploy bridge opens one PR per pipeline run, big tasks that should be decomposed into 3–4 PRs can't be. They're forced into one PR per pipeline run regardless of issue size.

## 2. Goals

- Add a `parent_issue_id` nullable self-referencing FK to the `issue` table.
- Parent issues (issues with open children) are **not work items** — the orchestrator-facing trigger path must refuse to run a pipeline against a parent.
- When a child issue closes, if all siblings are also closed, auto-close the parent.
- Issue detail UI surfaces the parent-child relationship and exposes a "create child" affordance.
- The engine stays agnostic — no hardcoded state/status/priority logic; auto-close uses the existing `close(id, version)` service method and records a normal `state_changed` event.

## 3. Non-goals

- **Depth / arbitrary nesting.** Schema allows any depth because it's a self-FK, but the UI and auto-close semantics are defined only for a single parent layer. If someone makes a grandchild, the schema tolerates it; the UI renders the immediate parent + immediate children only; auto-close propagates up exactly one level per closure event. Cascading up the tree works inductively because closing the parent fires its own `state_changed` handler, but no special multi-level logic is added.
- **Issue-type distinction between "epic" and "story".** There is no `is_epic` flag. "Parent-ness" is a runtime property: an issue is an epic iff it has at least one child. No type-catalog change required.
- **Automatic parent state transitions beyond close.** If all children close and the parent auto-closes, good. If a child reopens, the parent does **not** automatically reopen — the UI already shows the parent-child view, operator can reopen the parent manually.
- **Child-creation wizard with templates.** "Create child" is a minimal affordance: prefills `parent_issue_id`, reuses the existing `/issues/new` form.
- **Bulk move / re-parenting operations.** Post-alpha.
- **Cross-project parenting.** A child must live in the same project as its parent (enforced by FK cascade semantics — if a project is deleted, all its issues go, so cross-project FKs would be ambiguous; keep within-project only).
- **Deleting a parent that has children.** Out of scope for alpha — if the operator wants this, they re-parent or close children first. The schema uses `ON DELETE RESTRICT` on `parent_issue_id` to prevent accidental orphaning.
- **Separate "epic" view / roll-up dashboard.** Post-alpha.
- **Work-queue filtering.** The roadmap phrases the orchestrator requirement as "work queue filters out issues with open children." fluxaOS has no autonomous work queue today — every pipeline run is manually triggered through `pipeline.runs.trigger`. The correct shape for alpha is to enforce the rule at the trigger boundary (see Goal 2), not to build a queue abstraction we don't need.

## 4. Requirements

### R-EPIC.R1 — Schema: `parent_issue_id` on `issue`

- **Column:** `parent_issue_id uuid NULL REFERENCES issue(id) ON DELETE RESTRICT`
- **Invariant 1 (project scope):** a child's `project_id` must equal its parent's `project_id`. Enforced by a `CHECK` constraint backed by a subquery — or, since PostgreSQL doesn't allow subqueries in CHECK, by an `AFTER INSERT OR UPDATE OF parent_issue_id` trigger that raises on mismatch. The trigger is the canonical path.
- **Invariant 2 (no self-parent):** `parent_issue_id != id`. Enforced by `CHECK (parent_issue_id IS NULL OR parent_issue_id <> id)`.
- **Invariant 3 (no cycles for alpha):** not enforced in the DB. The UI offers only "create child" (FK always points to an existing parent from an issue being created fresh) — this means cycles are not reachable through the UI. Post-alpha if a re-parenting feature lands, cycle prevention comes with it.
- **Index:** `index issue_parent_idx on issue(parent_issue_id) where parent_issue_id is not null` — parent→children lookups are the hot path.
- **Migration file:** `drizzle/0009_r_epic.sql` (auto-generated by `npm run db:generate`, then hand-edited to add the trigger and partial index if the generator skips them).

### R-EPIC.R2 — Service layer: parent-child queries

- `issueService.getChildren(parentId: string): Promise<IssueSelect[]>` — ordered by `number ASC`.
- `issueService.getParent(childId: string): Promise<IssueSelect | null>` — returns null when `parent_issue_id` is null.
- `issueService.hasOpenChildren(parentId: string): Promise<boolean>` — count of `is_closed = false` children > 0.
- `issueService.countOpenChildren(parentId: string): Promise<number>` — exposed for UI badge ("3 open, 1 closed"); implementation returns both counts in one query.

### R-EPIC.R3 — Service layer: parent-aware create

- `issueService.create(input)` already exists. Extend the input schema to accept optional `parentIssueId: string`.
- When `parentIssueId` is provided: validate it exists, validate it's in the same project, write it to `parent_issue_id`. Trigger catches cross-project mismatches as a safety net.

### R-EPIC.R4 — Orchestrator-facing trigger rejects parent issues

- `pipeline.runs.trigger` mutation (the **only** user-facing path that kicks off a run) calls `issueService.hasOpenChildren(issueId)` before doing anything else.
- If true, throw a tRPC `BAD_REQUEST` with code `ISSUE_IS_EPIC` and message:
  > Issue has N open child issue(s). Run pipelines against the children, not the parent.
- UI surfaces the error: issue detail page disables "Run Stage" on the pipeline tracker (or returns an alert if somehow clicked). Disabled state is driven by the existing `pipelineState` query + a new `isEpic` signal returned from `issue.getById`.
- **Why this location, not inside `executeManualRun`:** the trigger is the single synchronous entry point a user can hit. By the time `executeManualRun` fires, we've already written a `pipeline_run` row and flipped it to `running`. Rejecting at the trigger avoids the bookkeeping mess of reverting a started run.

### R-EPIC.R5 — Auto-close parent on final child close

- Plumbing path: `issueService.transition()` and `issueService.stateOverride()` both call an internal helper `maybeAutoCloseParent(childId)` **after** writing the child's new state and emitting its `state_changed` event.
- `maybeAutoCloseParent` logic:
  1. Load the child row. If `parent_issue_id` is null, return.
  2. Load the parent row. If parent `is_closed` is already true, return.
  3. Load sibling counts: `select count(*) filter (where is_closed = false) from issue where parent_issue_id = <parent>`.
  4. If the open-count is 0, call `this.close(parentId, parent.version, 'orchestrator')` — same path the user-facing close mutation uses, so event bookkeeping is identical.
  5. Append a dedicated `issueEvent` with type `state_changed` and payload `{ reason: 'auto_close_all_children_closed', last_child: childId }` so the activity feed can render "closed automatically — all children closed." This event is in *addition* to the generic `state_changed` that `close()` already emits, because the reason is specific and worth surfacing.
- **Why an additive event, not overwriting `close`'s event:** `close()` is the shared path; its event payload is stable. Adding a secondary event with structured `reason` is strictly additive and doesn't break any existing consumer.
- **Concurrency:** if two children close simultaneously and both pass the "0 open siblings" check, both try to close the parent. The parent close uses optimistic-version locking (`assertVersion`) — the second write throws `VERSION_CONFLICT`. `maybeAutoCloseParent` catches `VERSION_CONFLICT` and re-reads the parent once: if it's now closed, swallow the error; if it's still open, the second close retries once. If the retry also fails, log and swallow — the parent will be visibly still open in UI, operator can close manually. (Alpha-acceptable; a nicer serialization comes post-alpha.)

### R-EPIC.R6 — Issue detail UI: parent + children + create child

- Issue detail page shows a new `RelationshipsCard` component between the header and the `IssueDetailEditors` panel.
- Card contents:
  - If `parent_issue_id` is set: a link row "Parent: #N — title" that navigates to the parent's detail page.
  - Children list (always shown when issue has at least one child): each row shows `#N  • <state>  • title`, clickable to the child's detail page. Closed children render with strikethrough + muted color. Sorted by `number ASC`.
  - "Create child issue" button that navigates to `/{org}/{user}/{project}/issues/new?parent=<uuid>`. The create page reads the query param and passes `parentIssueId` into the create mutation.
- If issue has neither parent nor children, the card is not rendered.
- Pipeline tracker on this page disables the "Run Stage" button when `isEpic` is true and shows an inline note: "This issue has open child issues. Run pipelines on the children."

### R-EPIC.R7 — Issue list UI: parent indicator

- Minimal addition: the existing `/issues` list already renders a row per issue. Add a small indicator (e.g., " ↳" prefix before the title when `parent_issue_id` is set, " ⊃ N" suffix when `hasOpenChildren`). No change to the list query shape — `issue.list` already returns the full row, which now includes `parent_issue_id`. The `hasOpenChildren` count is a separate lightweight query batched on the list page.
- Post-alpha: proper tree / indentation view. Alpha is flat list + indicators.

### R-EPIC.R8 — Realtime

- Supabase Realtime already subscribes to `issue` and `issue_event` table changes on the detail page (per R-REM-W2/W3-a). The schema change adds `parent_issue_id` but the realtime subscription is on the whole row — no adapter work needed, the new column propagates for free.
- When a child auto-closes a parent, the parent's detail page (if open in another tab) will receive the row update and the new `issue_event` row. The UI already re-renders on those. Verified as part of the journey test.

### 5.2 Migration (hand-edits on top of generator output)

```sql
-- drizzle/0009_r_epic.sql
ALTER TABLE "issue" ADD COLUMN "parent_issue_id" uuid;

ALTER TABLE "issue"
  ADD CONSTRAINT "issue_parent_fk"
  FOREIGN KEY ("parent_issue_id") REFERENCES "issue"("id")
  ON DELETE RESTRICT;

ALTER TABLE "issue"
  ADD CONSTRAINT "issue_no_self_parent"
  CHECK (parent_issue_id IS NULL OR parent_issue_id <> id);

CREATE INDEX "issue_parent_idx" ON "issue"("parent_issue_id")
  WHERE parent_issue_id IS NOT NULL;

-- Cross-project parenting guard (trigger-based because CHECK can't subquery)
CREATE OR REPLACE FUNCTION assert_issue_parent_same_project()
RETURNS trigger AS $$
DECLARE
  parent_project uuid;
BEGIN
  IF NEW.parent_issue_id IS NULL THEN
    RETURN NEW;
  END IF;
  SELECT project_id INTO parent_project FROM issue WHERE id = NEW.parent_issue_id;
  IF parent_project IS NULL THEN
    RAISE EXCEPTION 'Parent issue % not found', NEW.parent_issue_id;
  END IF;
  IF parent_project <> NEW.project_id THEN
    RAISE EXCEPTION 'Parent issue % is in a different project', NEW.parent_issue_id;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER issue_parent_same_project
BEFORE INSERT OR UPDATE OF parent_issue_id ON "issue"
FOR EACH ROW EXECUTE FUNCTION assert_issue_parent_same_project();
```

## 6. Invariants (new)

- **I-EPIC-1:** For any issue row, `parent_issue_id` is either NULL or references an existing issue in the same project.
- **I-EPIC-2:** No issue has itself as parent.
- **I-EPIC-3:** An issue with at least one open child cannot be the target of `pipeline.runs.trigger`.
- **I-EPIC-4:** When an issue transitions to an `is_terminal = true` state, if its parent has zero open children after the transition, the parent is atomically closed in the same request.

## 8. Open questions

None that block planning. The `maybeAutoCloseParent` concurrency retry is simple-minded (1 retry, then log+swallow) and is marked alpha-acceptable in R5. Post-alpha if it ever misfires, the fallback is explicit serialization via row-level `SELECT ... FOR UPDATE` inside a transaction.

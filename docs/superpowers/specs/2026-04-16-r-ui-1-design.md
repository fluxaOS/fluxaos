## Goal

Ship the settings-layer CRUD features required before beta:

1. **Driver settings page** — list all drivers (formerly "harness"), view, edit, toggle enabled.
2. **Skill settings page** — list, view, edit, delete (existing Create flow preserved).
3. **Shared `RecordEditor` primitive** — single reusable component that backs both pages and can be adopted by future settings pages (personas, routing, providers).
4. **Runtime feature-gating primitive** — `hasFeature()` function + `Feature` enum, always returning `true` today, wiring point for future SaaS tiers.
5. **Schema + code-wide rename** — `harness_catalog` → `driver` and every reference in source code, tests, tRPC routers, UI, migrations, and active docs.
6. **Terminology glossary seed** — `docs/terminology.md` with initial entries to prevent future naming drift.
7. **End-to-end journey tests** — six Playwright journeys, story-backed, covering the full CRUD lifecycle plus error and conflict paths.

Explicitly out of scope (deferred and tracked):
- Real-time updates (LiveOutput streaming, activity feed auto-refresh, duration updates) — R-UI-2
- Version history + revert for drivers and skills — DEF-003
- Preview/blur gate — DEF-001
- Role-based permissions — DEF-002
- Full subscription tier model — DEF-004
- Full schema-wide terminology doc — DEF-005 (seeded here, completed as future phases add terms)
- Cosmetic polish (tense, casing, "Closed" vs "Complete") — existing deferred entries

## Scope Decision: Rename as Phase 0

The `harness_catalog` → `driver` rename is a prerequisite step inside R-UI-1, not a separate phase. Reasoning:

- R-UI-1 features are built on top of the driver entity. A split between "R-RENAME" and "R-UI-1" creates a coordination gap where the driver settings page might land before the rename, forcing a second round of churn.
- The rename is one commit wave; features are another. Keeping them sequential inside one phase means one plan, one review, one verification cycle.
- If the rename runs into problems, the phase stops at that boundary and we reassess — no mid-flight split.

**Order of operations inside R-UI-1:**

1. Rename work (Phase 0): migration, schema, code, tests, active docs, router file rename.
2. Feature primitives (Phase 1): `RecordEditor` + `hasFeature()` + terminology doc seed.
3. Driver settings page (Phase 2).
4. Skill settings page (Phase 3).
5. Journey tests (Phase 4).
6. Verification.

## RecordEditor Primitive

### Purpose

A feature-agnostic, vendor-agnostic layout primitive for list + detail + edit UIs over CRUD entities. Takes a descriptor describing what fields exist and how to render them, plus mutation callbacks. Knows nothing about skills, drivers, or tRPC internals.

### Props

```ts
type RecordEditorProps<TRecord> = {
  descriptor: RecordDescriptor<TRecord>;
  records: TRecord[];
  isLoading: boolean;

  // Required mutations
  onSave: (id: string, patch: Partial<TRecord>, expectedVersion: number) => Promise<void>;

  // Optional mutations — absence hides the action button
  onDelete?: (id: string, expectedVersion: number) => Promise<void>;
  onToggleEnabled?: (id: string, enabled: boolean, expectedVersion: number) => Promise<void>;

  // Deferred-hook slots — no-ops today
  previewGate?: (record: TRecord) => React.ReactNode;      // DEF-001
  canEdit?: (record: TRecord) => boolean;                   // DEF-002
  canDelete?: (record: TRecord) => boolean;                 // DEF-002
  onEditSnapshot?: (record: TRecord) => void;               // DEF-003
};
```

### Descriptor shape

```ts
type RecordDescriptor<TRecord> = {
  entityName: string;                              // "driver", "skill" — used in messages
  title: (r: TRecord) => string;                   // primary label per row
  subtitle?: (r: TRecord) => string;               // secondary label per row
  fields: FieldDescriptor<TRecord>[];
  toggleEnabledField?: keyof TRecord;              // if set, shows toggle in list
};

type FieldDescriptor<TRecord> = {
  key: keyof TRecord;
  label: string;
  fieldType: 'text' | 'textarea' | 'textarea-large' | 'tags' | 'boolean' | 'readonly';
  required?: boolean;
  placeholder?: string;
  // Validation: descriptor-level rule, per field
  validate?: (value: unknown) => string | null;    // null = valid; string = error message
};
```

### Layout

Single-column: list on top, detail panel below when a row is selected. No modal, no blur (blur is DEF-001).

```
┌─────────────────────────────────────────────────────┐
│ List                                                │
│  ▸ Row 1  [title]  [subtitle]        [toggle ⬤]   │
│  ▸ Row 2  [title]  [subtitle]        [toggle ⬤]   │
│  ▸ Row 3  [selected — highlighted]   [toggle ⬤]   │
├─────────────────────────────────────────────────────┤
│ Detail panel                                        │
│  Row 3 — version 4 · updated 2m ago                 │
│  [fields rendered from descriptor]                  │
│  Actions bar:                                       │
│    viewing:  [Edit]                                 │
│    editing:  [Save] [Cancel] [Delete?]              │
│    confirming-delete: [inline confirmation]         │
└─────────────────────────────────────────────────────┘
```

### State machine (inside RecordActionsBar)

```
viewing ──Edit──▶ editing
editing ──Save──▶ saving ──success──▶ viewing (record refreshed)
editing ──Save──▶ saving ──conflict──▶ editing (toast shown, draft preserved)
editing ──Cancel──▶ viewing (draft discarded)
editing ──Delete──▶ confirming-delete
confirming-delete ──Cancel──▶ editing
confirming-delete ──Confirm──▶ deleting ──success──▶ viewing (record cleared)
confirming-delete ──Confirm──▶ deleting ──fk-error──▶ editing (toast with referenced-count)
```

### What RecordEditor does NOT do

- No direct tRPC imports — mutations are passed in
- No field type beyond the six listed — extend via descriptor if needed later
- No visual polish like drag-to-reorder, bulk actions, filters — out of scope
- No validation framework — descriptor provides per-field `validate` functions; that's it

## Feature Gating Primitive

### File

`src/core/features/features.ts`

### Shape

```ts
export enum Feature {
  PREVIEW_GATE = 'preview_gate',                   // DEF-001
  ROLE_BASED_PERMISSIONS = 'role_based_permissions', // DEF-002
  REVISION_HISTORY = 'revision_history',           // DEF-003
}

// DEF-004: wire to subscription state when SaaS tier model exists
export function hasFeature(userId: string, feature: Feature): boolean {
  return true; // Today: every feature is available to every user
}
```

### Usage

Pages pass `canEdit`, `canDelete`, etc. into RecordEditor using `hasFeature()` calls:

```ts
<RecordEditor
  canEdit={() => hasFeature(userId, Feature.ROLE_BASED_PERMISSIONS)}
  canDelete={() => hasFeature(userId, Feature.ROLE_BASED_PERMISSIONS)}
  onEditSnapshot={(r) => hasFeature(userId, Feature.REVISION_HISTORY) && snapshotRevision(r)}
/>
```

Today every call returns `true`, so every user sees every button. When subscription tiers arrive, `hasFeature()` is updated in one place and the UI adjusts automatically. No scattered conditionals.

## Data Flow

### Read

1. Page mounts → `trpc.driver.list.useQuery()` (or `trpc.skill.list.useQuery({ projectId })`)
2. `RecordEditor` receives records → renders list
3. User clicks row → local `selectedId` state → detail panel renders that record

### Update

1. User clicks Edit → `RecordActionsBar` enters `editing` → **`onEditSnapshot(record)` fires** (DEF-003 no-op today)
2. Draft state lives inside RecordEditor (not propagated to DB until Save)
3. User clicks Save → validate via descriptor → call `onSave(id, patch, expectedVersion)`
4. Page's `onSave` handler calls the tRPC mutation with `{ id, ...patch, version }`
5. Router validates `WHERE version = $expected` (optimistic lock)
6. On success → returns updated record → client invalidates list query → RecordEditor re-renders with fresh record → state returns to `viewing`
7. On version mismatch → router throws → `onSave` rejects → toast shown → state stays `editing`, draft preserved

### Delete (skills only)

1. User clicks Delete → enter `confirming-delete` state with inline confirmation
2. User confirms → check `canDelete()` (DEF-002 stub) → call `onDelete(id, expectedVersion)`
3. On FK violation → toast with reference counts, state returns to `editing`
4. On success → list invalidated, selectedId cleared, detail panel shows empty state

### Toggle enabled (drivers only)

1. Toggle switch in list row fires `onToggleEnabled(id, !current, expectedVersion)`
2. Uses the standard `driver.update` mutation under the hood — sends `{ isEnabled: !current, version }`
3. Optimistic UI update, rollback on failure

### tRPC mutations — new and existing

| Mutation | Status | Needed for |
|---|---|---|
| `driver.list()` | EXISTS (renamed from `harness.list`) | list view |
| `driver.update({ id, ..., version })` | EXISTS (renamed) | edit + toggle |
| `driver.getById({ id })` | EXISTS (renamed) | optional |
| `skill.list({ projectId })` | EXISTS | list view |
| `skill.update({ id, ..., version })` | **NEW** | edit |
| `skill.delete({ id, version })` | **NEW** | delete |
| `skill.countReferences({ id })` | **NEW** | drives FK-error message content |

## Error Handling

### Validation (client-side)

Required field empty → red outline, inline "Required" label, Save disabled. No mutation attempt.

### Optimistic lock failure (409 conflict)

Inline banner (not a transient toast) with text: *"This record was updated elsewhere. Refresh to see the latest, or continue editing to overwrite."*

The banner contains a **"Refresh" action button** that:
1. Invalidates the list query so the component re-receives the server state
2. Clears the draft
3. Returns the state machine to `viewing`

State stays `editing` until the user clicks Refresh. Draft is preserved. Save-again without refreshing will fail again with the same conflict — `expectedVersion` in state is the stale one until Refresh runs.

MVP does not implement three-way merge. Deferred if ever needed.

**Both drivers and skills use this identical flow.** Optimistic lock is enforced in the tRPC routers on both `driver.update` and `skill.update` — and on `skill.delete` (skill delete takes `{ id, version }` and validates the version before running `countReferences` + delete).

### Referential integrity (FK violation on delete)

Delete mutation first runs `countReferences(id)` to get referenced counts. If non-zero, mutation rejects without attempting delete and returns counts in the error payload. Toast:

> *"Cannot delete '{title}' — referenced by {n} pipeline stages and {m} stage runs. Remove references first, or disable instead."*

For skills (no isEnabled today), the "disable instead" sentence is omitted.

### Generic network error

Toast: *"Save failed. Check your connection and try again."* State stays `editing`.

### Edge cases

- Empty list → EmptyState with descriptor-provided message
- Loading → existing SkeletonTable for list, simple shimmer for detail
- Mutation in flight → Save/Cancel/Delete disabled, spinner on active button

## Descriptors

### Driver descriptor

Exposes **every runtime-consumed column** so admins can reconfigure invocation without editing code. Notably includes `outputFormatFlag` and `contextLayout` — both are read by the orchestrator (command-builder consumes `outputFormatFlag`; stage-runner consumes `contextLayout` to decide the instructions-file name, e.g. `CLAUDE.md` vs `AGENTS.md`). Omitting them from the UI silently locks those values at seed-time.

```ts
// src/app/[org]/[user]/[project]/settings/drivers/descriptor.ts
export const driverDescriptor: RecordDescriptor<Driver> = {
  entityName: 'driver',
  title: (d) => d.name,
  subtitle: (d) => d.slug,
  fields: [
    { key: 'name', label: 'Name', fieldType: 'text', required: true },
    { key: 'slug', label: 'Slug', fieldType: 'text', required: true },
    { key: 'binary', label: 'Binary', fieldType: 'text', required: true,
      placeholder: 'claude' },
    { key: 'modelFlag', label: 'Model flag', fieldType: 'text',
      placeholder: '--model' },
    { key: 'dirFlag', label: 'Directory flag', fieldType: 'text',
      placeholder: '--cwd' },
    { key: 'sessionNameFlag', label: 'Session-name flag', fieldType: 'text' },
    { key: 'promptTransport', label: 'Prompt transport', fieldType: 'text',
      placeholder: 'stdin | argv | file' },
    { key: 'outputFormat', label: 'Output format', fieldType: 'text',
      placeholder: 'stream-json | text' },
    { key: 'outputFormatFlag', label: 'Output-format flag', fieldType: 'text',
      placeholder: '--output-format' },
    { key: 'promptSendDelayMs', label: 'Prompt send delay (ms)', fieldType: 'text' },
    { key: 'probeCommand', label: 'Probe command', fieldType: 'text' },
    { key: 'notes', label: 'Notes', fieldType: 'textarea' },
    { key: 'issuePromptTemplate', label: 'Issue prompt template', fieldType: 'textarea-large' },
    { key: 'queuePromptTemplate', label: 'Queue prompt template', fieldType: 'textarea-large' },
    // JSON-valued fields shown read-only for MVP (DEF: structured JSON editor is a future phase)
    { key: 'defaultArgs', label: 'Default args (JSON)', fieldType: 'readonly' },
    { key: 'envVars', label: 'Env vars (JSON)', fieldType: 'readonly' },
    { key: 'extraArgs', label: 'Extra args (JSON)', fieldType: 'readonly' },
    { key: 'contextLayout', label: 'Context layout (JSON)', fieldType: 'readonly' },
    { key: 'version', label: 'Version', fieldType: 'readonly' },
  ],
  toggleEnabledField: 'isEnabled',
};
```

**Why `defaultArgs` / `envVars` / `extraArgs` / `contextLayout` are readonly in MVP:** These are `jsonb` columns with non-trivial structure. A plain textarea is a footgun (one typo → broken JSON → orchestrator crash). A proper structured editor (e.g., Monaco with JSON schema validation) is out of scope for R-UI-1 and added as a new deferred entry (DEF-006).

## Risks

1. **Rename scope underestimated.** 24 source files + 7 migrations + 1 test + ~5 active docs. Mitigation: run `grep -r 'harness\|Harness\|HARNESS'` after each commit of the rename wave to verify no residual references.

2. **Drizzle rename migration.** Renaming a table with foreign keys requires a specific migration sequence. Mitigation: generate the migration via `drizzle-kit generate` rather than hand-writing; test on a fresh DB (`nuke → migrate → seed → verify:seed`) before merging.

3. **`promptTemplate` UX is cramped.** Skill and driver prompt templates can be hundreds of lines. A plain `<textarea>` may feel small. Mitigation: `fieldType: 'textarea-large'` renders a min-height of 20 rows with auto-grow; if that's insufficient after browser verification, a DEF entry opens for a future editor upgrade (Monaco, etc.).

4. **Conflict-on-save journey is flaky.** Two-context Playwright tests are historically flakier than single-context. Mitigation: explicit `waitFor` on network state between tab operations; if flaky after implementation, the journey stays in the suite but runs as `@slow` and we add a deferred entry to stabilize.

5. **`isEnabled` field already exists on `harness_catalog` as `isEnabled`.** Confirmed in schema — no new migration for the field itself, only the column rename.

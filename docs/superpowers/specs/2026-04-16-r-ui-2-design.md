# R-UI-2 — Real-time Updates — Design Spec

**Date:** 2026-04-16
**Depends on:** R-UI-1 (complete), R5-V (complete — schema + manual run), R5.5 (complete — IPC)
**Succeeded by:** R6 (Polish + Ship)
**Status:** Draft — awaiting approval

---

## Why this phase exists

R5-V's design spec (`docs/superpowers/specs/2026-04-12-r5v-manual-execution-design.md`) describes the full realtime pipeline: the orchestrator runs as a systemd-managed Node.js process, subscribes to Supabase Realtime, and drives stage runs through a deterministic state machine; the browser subscribes to Realtime and renders events as they arrive; crash recovery is handled via `restart-unless-stopped` semantics with a retry budget. R5-V's implementation shipped the schema, the UI components, and a direct "manual run" code path — but stopped short of the realtime plumbing.

What actually landed in main:
- `LiveOutput.tsx` and `RunDetailModal.tsx` call `supabase.channel().on('postgres_changes', …)` directly, bypassing the `RealtimeProvider` port.
- The handler calls `eventsQuery.refetch()` on every INSERT instead of appending the payload. The user-visible effect is output that appears in a batch at run completion.
- The issue activity feed has no Realtime subscription at all. It refetches only on local mutation success.
- `src/adapters/supabase/realtime.ts` (the one file where Supabase's Realtime SDK is allowed to appear) does not exist.
- `event-orchestrator.ts` is defined but never instantiated in production. Manual runs bypass it entirely.
- Duration in `RunDetailModal` reflects the last refetch, not elapsed time.

R-UI-2 finishes R5-V. No new concepts. No new schema. The design already exists in R5-V; R-UI-2 ships the missing implementation and verifies it against R5-V's own exit criteria.

This phase also codifies the vendor-agnostic principle that grounds the whole rebuild. "If you find yourself typing a vendor name inside `core/` — you're doing it wrong" (per the Adapter Architecture diagram in `docs/planning/brainstorming-diagrams/`). R-UI-2 makes that true for Realtime by routing every subscription through the port, with Supabase's SDK quarantined to one adapter file.

## Scope

### In scope

1. **Write the Supabase Realtime adapter.** Implement `RealtimeProvider` (defined at `src/core/ports/realtime.ts`) in a new file `src/adapters/supabase/realtime.ts`. This is the only place in the repository where `@supabase/*` Realtime APIs may be imported outside of the existing `src/lib/supabase/` harness code.

2. **Expose the adapter to client components through a context.** Add a React context provider near the App Router root and a `useRealtime()` hook in `src/lib/realtime/` so client components get the `RealtimeProvider` port rather than constructing a Supabase client.

3. **Route all three client subscription sites through the port.**
   - `LiveOutput.tsx` — replace the direct `supabase.channel()` call with `useRealtime().subscribeToTable(…)`.
   - `RunDetailModal.tsx` — same.
   - Issue detail client (`src/app/[org]/[user]/[project]/issues/[number]/client.tsx`) — add a new subscription for the activity feed (`issue_event` table filtered by `issueId`). This is a new subscription, not a rewrite.

4. **Stream events as they arrive.** Replace the refetch-on-INSERT pattern with direct payload append. When a new `event` row arrives, it is appended to the React Query cache for that `stageRunId` via `setQueryData`. The tRPC query remains the source of truth for initial load; the cache is mutated additively thereafter. On UPDATE events (for `stage_run` / `pipeline_run`), the cache entry is merged in place. This kills the batching symptom at its source.

5. **Tick duration for running stages.** `RunDetailModal.tsx` currently computes duration from `startedAt` and the last query result. Add a `useNow()` hook that triggers a re-render each second while the stage is active, so the displayed duration updates without needing a Realtime event. This is a display-layer change only.

6. **Run the orchestrator as a systemd-managed Node.js process.**
   - Add an orchestrator entrypoint script at `src/core/orchestrator/main.ts` (or equivalent) that constructs a server-side `RealtimeProvider` adapter instance, a server-side `Database`, a `StageExecutor`, and calls `createEventOrchestrator(...)`, then `start()` + `recoverOnStartup()`.
   - Add a systemd unit file under a tracked path (e.g. `scripts/systemd/fluxaos-orchestrator.service`) so the daemon can be installed on any fluxaOS host.
   - Add an install script (e.g. `scripts/install-orchestrator.sh`) that copies the unit file into `~/.config/systemd/user/` (user-level service, no root required on the homelab), runs `systemctl --user daemon-reload`, and enables + starts the service.
   - Document the install in `CLAUDE.md` and `docs/session-quick-start.md`.
   - Manual runs continue to use their current direct path. The orchestrator is live but handles nothing user-visible today. This is intentional; wiring manual runs through the orchestrator is a follow-on phase (R6 or later), not R-UI-2.

7. **Route orchestrator stage dispatch through BullMQ.** The existing `src/adapters/bullmq/queue.ts` adapter and `src/core/orchestrator/stage-worker.ts` worker already exist but are not wired to the event-orchestrator's live code path. R-UI-2 connects them: when the orchestrator decides to run a stage, it enqueues a job on the `stage-runs` BullMQ queue; the stage-worker consumes jobs and invokes `executeStageRun`. This is the Celery-equivalent durability layer — if the orchestrator (or worker) crashes with an un-ack'd job, BullMQ redelivers it to a healthy instance on restart. No re-attach logic required for the common case.

8. **Implement orchestrator startup recovery.** The `recoverOnStartup()` method declared in `event-orchestrator.ts` is unimplemented. Implement it per the R5-V spec (lines 149–170) and D1 above: on boot, scan for `stage_run` rows with status `running` or `launching`. For each:
   - If the row has a corresponding un-ack'd BullMQ job, leave it alone — BullMQ will redeliver when a worker is available.
   - If no BullMQ job exists (orphaned stage_run), check `attempt` against `maxRetries` on `pipeline_stage`. If within budget, enqueue a new BullMQ job with `attempt + 1`. If budget exhausted, mark the stage_run `failed` with an `ERROR` event containing "retry budget exhausted."
   - If `pid` is still alive but no BullMQ job exists (orphaned subprocess), mark `failed` with an `ERROR` event stating "orphaned subprocess — orchestrator restarted without re-attach." Subprocess re-attach is explicitly deferred per D1.
   - Rows with status `cancelled` are never re-launched. Skip them.

9. **Explicit Supabase Realtime publication migration.** Supabase Cloud auto-publishes tables to `supabase_realtime` by default on the managed service, but that's not guaranteed and not version-controlled. Add a migration (`drizzle/XXXX_realtime_publication.sql`) that runs `ALTER PUBLICATION supabase_realtime ADD TABLE event, stage_run, pipeline_run, issue_event;` with `CREATE PUBLICATION … IF NOT EXISTS` guards so a fresh DB comes up correctly.

10. **Fold in adjacent deferred fixes that would otherwise require re-touching the same files.**
   - **GateResultsPanel rule-detail rendering.** `GateResultsPanel.tsx` expects `ruleResults[].field` but the stored `RuleResult` nests fields under `rule.rule.field`. Two-line fix. Lives in `RunDetailModal`'s right panel — fixing now avoids a later touch.
   - **Cancel-button verification.** Cancel buttons on run and stage exist but were never exercised against a running stage. Since we're activating the orchestrator, the cancel path becomes real. Covered by a new journey test (below).
   - **Rewrite skipped orchestrator tests.** `src/__tests__/integration/orchestrator.test.ts` is `.skip`'d because it targeted the deleted polling-manager. Since the orchestrator becomes live code in this phase, its tests must be real. Rewrite for the event-orchestrator: instantiate it against a real Supabase, create a pipeline_run, assert it picks up the INSERT and drives stages forward.
   - **Conflict-on-save `networkidle` — already fixed** in R-UI-1 Session D (noted here because it was a known R-UI-2 blocker).

### Out of scope (and why)

- **Casing/tense inconsistency; "Closed" vs "Complete" label.** Cosmetic, codebase-wide, orthogonal to realtime. Each has a deferred-fix entry and will be picked up in its own cosmetic pass.
- **Scheduled / cron-triggered pipeline runs.** No use case exists yet. Adding one is speculative scope.
- **RLS / auth changes.** Realtime works in dev without RLS changes. When real auth lands it will come with its own RLS pass.
- **Wiring manual runs through the orchestrator.** The R5-V spec's end-state is that every run (manual or automatic) goes through the orchestrator. Today manual runs bypass it. R-UI-2 does not change that — the orchestrator runs and handles its own state machine, manual runs continue on their current direct path. The switch-over is a follow-on.
- **Mission Control view.** The rebuild spec (R5-V spec section "Mission Control") describes a future dashboard. Not in R-UI-2.
- **CLI parity for realtime.** The rebuild spec requires it (journey steps 55–58). Deferred to R6.

## Architectural principles (inherited, not new)

All of these come directly from `docs/invariants.md`, the R5-V architectural cleanup design, and the rebuild spec. R-UI-2 adds zero new principles; it fulfills them.

1. **Zero vendor imports in `src/core/`.** (Invariant 7.) `event-orchestrator.ts` already receives a `RealtimeProvider` port, not a `SupabaseClient`. R-UI-2 adds the adapter without changing the port.
2. **All services use dependency injection.** (Invariant 8.) The client-side context provider and the server-side orchestrator entrypoint both construct adapters at the composition root; no module-scope singletons.
3. **Everything is config-driven. No fallback defaults.** (Invariant 9.) If Supabase env vars are missing, the adapter throws at construction, not at first subscription.
4. **No unit tests. Integration tests hit real Supabase.** (Invariants 15–16.) Realtime adapter tests, if any, exercise a live Supabase channel end-to-end against the real managed service.
5. **The journey test is the real test.** (Invariant 17.) New Playwright journeys cover the new behavior; a human walks the app in a browser before merge.
6. **Real-time observability is required.** (Invariant 18.) This phase delivers exactly that.
7. **Supabase Realtime is the streaming mechanism. No fallbacks.** (R5-V spec Principle 3.) If the WebSocket drops, the client reconnects silently. No "reconnecting…" banners, no polling fallback.
8. **Restart-unless-stopped.** (R5-V spec Principle 5.) The orchestrator re-launches failed stages within the retry budget on boot, unless explicitly cancelled.
9. **No hardcoded stage / provider / driver / model names.** (Invariants 1–4.) Realtime subscriptions are keyed by row IDs and table names, never by domain-specific literals.
10. **GTM-portable privilege model.** (New — enforced per D2.) The orchestrator and stage-worker code must not assume the privilege level under which they run. Specifically:
    - No reads or writes anchored to `$HOME`, `$XDG_*`, or `process.env.USER`.
    - All filesystem paths (workspace root, log destinations, unit-file templates, install targets) sourced from `.env` or passed-in config, never derived from user-profile conventions.
    - No hardcoded listen addresses; any bindings read from env.
    - Logs go to stdout/stderr and are captured by `journalctl`. Identical behavior for user-level and system-level units.
    - The systemd unit file is a template: the only diff between user-level (R-UI-2) and system-level (GTM) deployment is the install target path and an optional `User=` directive. No application code changes.

```
┌──────────────────────────────────────────────────────────┐
│  Browser — Next.js App Router                            │
│                                                          │
│  <RealtimeContextProvider>  ← constructed at root        │
│    │  provides useRealtime() → RealtimeProvider          │
│    │                                                     │
│    ├── LiveOutput                    ─┐                  │
│    ├── RunDetailModal                ─┼─ subscribeToTable│
│    └── Issue activity feed (new)     ─┘    via port      │
└───────────────────────────┬──────────────────────────────┘
                            │ WebSocket (Realtime)
                            │
                    ┌───────┴───────┐
                    │  Supabase     │
                    │  Realtime     │
                    │  (cloud)      │
                    └───────┬───────┘
                            │
┌───────────────────────────┴──────────────────────────────┐
│  systemd --user service: fluxaos-orchestrator            │
│  Node.js process, entrypoint src/core/orchestrator/main  │
│                                                          │
│  createEventOrchestrator(db, executor, realtime, queue)  │
│    ├── start()              ← subscribe to pipeline_run, │
│    │                          stage_run changes;         │
│    │                          enqueue stage jobs to      │
│    │                          BullMQ on dispatch         │
│    └── recoverOnStartup()   ← reconcile in-flight work:  │
│                                leave BullMQ-tracked      │
│                                jobs alone, fail orphans  │
└────────────────────┬─────────────────────────────────────┘
                     │
                     │ BullMQ enqueue
                     ▼
┌──────────────────────────────────────────────────────────┐
│  systemd --user service: fluxaos-stage-worker            │
│  Node.js process (can scale horizontally)                │
│                                                          │
│  BullMQ worker consumes stage-run jobs:                  │
│    executeStageRun(stageRunId) → spawns subprocess →     │
│    streams stdout to `event` table → completes run       │
│                                                          │
│  On un-ack'd crash: BullMQ redelivers job to a healthy   │
│  worker. Celery-equivalent durability.                   │
└────────────────────┬─────────────────────────────────────┘
                     │ writes to DB
                     ▼
                 (Supabase Postgres — which pushes
                  changes back out through Realtime)
```

Both browser-side and server-side actors talk to the same Supabase Realtime service through the same `RealtimeProvider` port. Each constructs its own adapter instance at its own composition root. The orchestrator and stage-worker coordinate through BullMQ, not directly — the orchestrator never invokes the worker in-process. This matches the rebuild-spec's two-container infrastructure model (fluxaos web app + redis) where BullMQ sits on redis and both orchestrator and worker are workloads of the fluxaos container.

## Component-level design

### `src/adapters/supabase/realtime.ts` — the Realtime adapter (NEW)

Implements `RealtimeProvider` exactly as declared at `src/core/ports/realtime.ts:9–26`. No new methods, no extended types.

**Construction.** Factory function `createSupabaseRealtimeAdapter(client: SupabaseClient): RealtimeProvider`. Accepts a pre-constructed Supabase client so it works equally for browser-side (`createBrowserClient` from `@supabase/ssr`) and server-side (`createClient` from `@supabase/supabase-js`) clients. Zero hidden dependencies.

**Port signature change.** Before the adapter can be written, `RealtimeProvider.subscribeToTable` at `src/core/ports/realtime.ts` is extended with an optional `filter?: string` parameter. The filter is a PostgREST-style row filter string such as `stage_run_id=eq.<uuid>` passed straight through to Supabase's `postgres_changes` config. R-UI-2 adds this to the port (keeping the port vendor-agnostic in spirit — the filter grammar is a simple column=operator.value DSL, not a Supabase type).

Updated port declaration:

```typescript
subscribeToTable<T>(
  channelName: string,
  table: string,
  event: 'INSERT' | 'UPDATE' | '*',
  callback: (payload: RealtimeTableEvent<T>) => void,
  filter?: string,
): Unsubscribe;
```

**`subscribeToTable` adapter behavior.** Wraps `client.channel(channelName).on('postgres_changes', { event, schema: 'public', table, filter }, handler).subscribe()` where `filter` is omitted from the config object when undefined (Supabase requires omission, not `undefined`). Translates the Supabase payload (`eventType`, `new`, `old`) into the port's `RealtimeTableEvent<T>`. Returns an `Unsubscribe` closure that calls `client.removeChannel(channel)`.

**`subscribe` (generic).** Wraps `client.channel(channel).on('broadcast', { event }, handler).subscribe()`. Same unsubscribe pattern.

**`broadcast`.** Wraps `client.channel(channel).send({ type: 'broadcast', event, payload })`. Returns a Promise.

**Error handling.** Subscription-level errors (invalid channel name, auth failure) throw from the factory call, not silently. Per-event handler errors are logged but do not kill the subscription.

**File budget.** ≤150 lines. Adapter files are thin.

### `src/lib/realtime/` — client context (NEW)

- `context.tsx` — a React context wrapping a `RealtimeProvider` instance constructed from `createBrowserClient()`. Provider component mounted once, near the App Router root.
- `use-realtime.ts` — the `useRealtime()` hook that consumes the context and returns the port. Throws if called outside the provider.
- `use-now.ts` — a small `useNow(intervalMs)` hook that returns a `Date` ref that updates at a chosen cadence. Used by `RunDetailModal` for live duration. Not realtime-related per se, but lives in the same directory because it's a neighbor concept.

**Why a context and not a hook-per-call-site.** A single shared adapter means a single WebSocket connection, fewer channel races, and one place to handle reconnect. Hook-per-call-site would multiply sockets unnecessarily.

### Three subscription-site changes

All three sites use the 5-argument form: `subscribeToTable(channelName, table, event, callback, filter?)`.

1. **`LiveOutput.tsx`.** Remove the `createClient()` + `supabase.channel()` block. Replace with:
   ```typescript
   useRealtime().subscribeToTable<EventRow>(
     `live-output-${stageRunId}`,   // channelName (unique per stageRun)
     'event',                        // table
     'INSERT',                       // event
     handler,                        // callback
     `stage_run_id=eq.${stageRunId}`, // filter
   );
   ```
   Handler calls `utils.pipeline.runs.events.setData({ stageRunId }, old => (old ? [...old, row] : [row]))` to append the row to the tRPC cache. Effect cleanup calls the returned `Unsubscribe`.

2. **`RunDetailModal.tsx`.** Same treatment for the `stage_run` UPDATE subscription:
   ```typescript
   useRealtime().subscribeToTable<StageRunRow>(
     `run-detail-${runId}`,
     'stage_run',
     'UPDATE',
     handler,
     `pipeline_run_id=eq.${runId}`,
   );
   ```
   On UPDATE, the handler merges the updated row into the existing `pipeline.runs.get` query cache entry. Duration tick added via `useNow({ enabled: isRunActive })` that drives a re-render each second.

3. **Issue activity feed** (`src/app/[org]/[user]/[project]/issues/[number]/client.tsx`):
   ```typescript
   useRealtime().subscribeToTable<IssueEventRow>(
     `issue-events-${issue.id}`,
     'issue_event',
     'INSERT',
     handler,
     `issue_id=eq.${issue.id}`,
   );
   ```
   Handler appends to the existing `issue.event.list` query cache keyed by the current filter selection.

All three follow the same shape: subscribe in a `useEffect` keyed by the filter ID, append on event, unsubscribe on cleanup. No refetch on event.

### `src/adapters/supabase/server-client.ts` — server-side client factory (NEW)

Exports a `createServerSupabaseClient()` function that reads env vars and returns a configured `@supabase/supabase-js` client suitable for Node-side use (no cookie-based session store, uses service role key when available and falls back to publishable key). This keeps the Supabase import inside the adapter layer where invariant 7 permits it.

```typescript
// Signature:
export function createServerSupabaseClient(): SupabaseClient
// Throws if required env vars are missing. Fail-fast per invariant 9.
```

### `src/core/orchestrator/main.ts` — server entrypoint (NEW)

Entrypoint for `fluxaos-orchestrator.service`. **Contains zero vendor imports.** Wiring:

1. Call `bootstrap()` from `@/config/bootstrap` — this registers db, executor, queue, auth in the registry.
2. Resolve dependencies: `registry.get<Database>('database')`, `registry.get<StageExecutor>('executor')`, `registry.get<QueueProvider>('queue')`.
3. Construct the server-side realtime adapter via the adapter-layer factory:
   ```typescript
   import { createServerSupabaseClient } from '@/adapters/supabase/server-client';
   import { createSupabaseRealtimeAdapter } from '@/adapters/supabase/realtime';
   // ...
   const realtime = createSupabaseRealtimeAdapter(createServerSupabaseClient());
   ```
4. `const orchestrator = createEventOrchestrator(db, executor, realtime, queue);`
5. `await orchestrator.recoverOnStartup();`
6. `orchestrator.start();`
7. Register SIGINT / SIGTERM handlers that call `orchestrator.stop()`.

**Invariant 7 compliance.** `src/core/orchestrator/main.ts` imports only from `@/config/*`, `@/adapters/supabase/*` (allowed — the adapter layer is the boundary), and `./event-orchestrator`. It never imports from `@supabase/*` directly. The vendor construction lives in `src/adapters/supabase/server-client.ts`.

**Why `main.ts` and not `worker.ts` or `daemon.ts`.** Naming convention match: `src/core/db/nuke.ts`, `src/core/db/seed.ts` — single-purpose entrypoint scripts at the file level. `main` is the unambiguous name.

### `event-orchestrator.ts` `recoverOnStartup()` — REPLACE existing implementation

**Current state** (read `src/core/orchestrator/event-orchestrator.ts:345-391` for the authoritative source):

```typescript
async function recoverOnStartup(): Promise<void> {
  const staleRuns = await db.select().from(stageRun)
    .where(eq(stageRun.status, STAGE_RUN_STATUS.running));

  for (const sRun of staleRuns) {
    const alive = sRun.pid ? isProcessAlive(sRun.pid) : false;
    if (!alive) {
      const [stage] = await db.select().from(pipelineStage)
        .where(eq(pipelineStage.id, sRun.pipelineStageId));
      // ... mark failed, check maxRetries, re-launch or fail pipeline
    }
  }
}
```

This existing implementation is **synchronous-execution-era code**. It called `launchStage` directly, assuming the orchestrator itself would spawn the subprocess. Under the BullMQ-mediated architecture R-UI-2 adopts, stages are never spawned by the orchestrator — they're enqueued — so the old logic's final step (`launchStage(run, stage)`) is wrong.

**Replacement algorithm** (per D1). The key change from the current implementation is the addition of a BullMQ job-status check as the first branch:

1. Query `stage_run` rows with status IN (`running`, `launching`). (Current implementation only checks `running` — adding `launching` catches stages enqueued but not yet picked up when the worker crashed.)
2. For each row:
   - **Branch (a) — BullMQ has an active/waiting/delayed job for this stageRunId.** Leave it alone; BullMQ (or its retry mechanism per D1-resolution below) will redeliver. Log `leaving to queue redelivery`. Skip to next row.
     - *Implementation note:* `queue.getJob('stage-runs', sRun.id)` returns `null` for both "never existed" AND "failed set (dead-letter)." We must treat `null` and `job.status === 'failed'` both as "no live job" and fall through to branch (b) or (c). Only `job.status IN ('active', 'waiting', 'delayed')` counts as "has the job."
   - **Branch (b) — no live job, subprocess dead (or no pid).** Read `attempt` and stage's `maxRetries`. If `attempt < maxRetries + 1`, enqueue a new BullMQ job for this stageRunId with `attempt + 1`. Else mark `failed` with event `{ reason: 'retry_budget_exhausted', attempt, maxRetries }`.
   - **Branch (c) — no live job, subprocess (`pid`) is alive.** Mark `failed` with event `{ reason: 'orphaned_subprocess', pid }`. R-UI-2 does not re-attach. Operator can manually `kill` the orphan. (PID recycling caveat: `process.kill(pid, 0)` returning success could mean a recycled PID belongs to an unrelated process. False-positive here results in the same outcome — marking failed with `orphaned_subprocess` reason — instead of branch (b)'s `retry_budget_exhausted` reason. Outcome identical; only the payload reason differs. Acceptable for R-UI-2.)
3. Skip rows with status `cancelled`. Never re-launched under any recovery path.

**Why this is a replacement, not a net-new implementation.** The current `recoverOnStartup` runs on startup. It must be fully replaced (not incrementally edited) because its core decision — "re-launch via `launchStage`" — is incompatible with the BullMQ-mediated architecture. The new algorithm reuses `isProcessAlive` helper but replaces the branching logic entirely.

### D1-resolution — BullMQ retry budget vs orchestrator retry budget

The original D1 description mentioned `attempts: 1` at the BullMQ level ("retry decisions live with the orchestrator, not BullMQ"). **That contradicts the Celery-equivalent-durability claim**: with `attempts: 1`, a worker crash (SIGKILL mid-job) causes BullMQ to move the job to the failed set after lockDuration expiry — there is no automatic redelivery. R-UI-2 resolves this explicitly:

- **BullMQ is configured with `attempts: 3, backoff: { type: 'exponential', delay: 2000 }`.** This gives native automatic redelivery on worker crashes, matching Celery's unack-redelivery behavior. Up to 3 attempts total (1 initial + 2 retries) for any job that never reaches a clean ack (worker SIGKILLed, lock expired, transient Redis disconnect).
- **`recoverOnStartup` is the reconciliation path for stage_runs whose BullMQ attempts are exhausted** (i.e., moved to the failed set), and for stage_runs whose BullMQ entry is missing entirely (orchestrator crashed before enqueue completed; queue flushed; etc.).
- **Orchestrator-level retry budget (`pipeline_stage.maxRetries`) is the SKILL-LEVEL retry budget.** A BullMQ retry is a "the worker crashed, re-run the same stage_run" retry. An orchestrator retry is a "the stage_run completed with a failure verdict, create a NEW stage_run with a new attempt number" retry. They serve different purposes:
  - BullMQ retry = infrastructure durability (the worker died; re-run the same stageRunId from scratch).
  - Orchestrator retry = application-level rework (the skill failed verdict; new stageRunId, new attempt, driven by `applyVerdict`).
- These two retry budgets operate independently and can NOT double-count. The BullMQ retry re-executes the SAME stageRunId row; the orchestrator creates a NEW stageRunId row with `attempt = previous + 1`. The key insight: same-id re-execution vs new-id re-execution are distinct observations in the DB audit trail.

Exit criterion 8 ("BullMQ absorbs stage-worker crashes") now passes on the BullMQ-native redelivery path; it does NOT depend on `recoverOnStartup`.

### `executeStageRun` re-entry guard (MODIFY) — new for v3

BullMQ's redelivery semantics (attempts: 3) mean `executeStageRun` may be invoked multiple times on the same `stageRunId`. Today `executeStageRun` (`src/core/orchestrator/stage-runner.ts:77`) has no guard — it unconditionally re-marks the row `running`, re-materializes workspace, re-spawns subprocess. A redelivery after SIGKILL would produce duplicate `launched`/`completed` events and a second workspace, corrupting the audit trail.

**Fix.** Add a status guard as the first step after loading `sRun`:

```typescript
// Re-entry guard: BullMQ may redeliver the same stageRunId (attempts: 3).
// Only fresh jobs (queued/launching) may execute; anything else is a stale redelivery.
if (
  sRun.status !== STAGE_RUN_STATUS.queued &&
  sRun.status !== STAGE_RUN_STATUS.launching
) {
  console.log(
    `[stage-runner] skipping stale redelivery for ${stageRunId} (status=${sRun.status})`,
  );
  // Return a zero-duration "already-handled" result so the caller treats this
  // as a successful no-op. The worker acks the BullMQ job and moves on.
  return {
    exitCode: 0,
    durationMs: 0,
    stageName: '',
    driverName: '',
    providerName: null,
    modelIdentifier: null,
    issueId: null,
    stageId: sRun.pipelineStageId,
    skillSignal: null,
    skillSignalReason: null,
    skillMetadata: null,
  };
}
```

This makes the function idempotent on the stageRunId key: once a stage_run has transitioned past `queued`/`launching` (to `running`, `completed`, `failed`, `cancelled`, `timed_out`), any later invocation is a no-op.

Callers (manual-run and the stage-worker's BullMQ handler) do not need to change — they just receive an empty-ish result and their existing terminal-state-handling logic continues to work.

### Stage-worker + BullMQ wiring (MODIFY)

Both `src/adapters/bullmq/queue.ts` and `src/core/orchestrator/stage-worker.ts` already exist. They're wired through the adapter registry but the orchestrator currently invokes `executeStageRun` in-process rather than enqueuing. R-UI-2 changes that:

- **Orchestrator dispatch.** `event-orchestrator.ts`'s stage-launch path replaces its current direct call with `queue.enqueue('stage-runs', stageRunId, { attempt })`. The orchestrator is now a state-machine-only actor; it does not execute stages in its own process.
- **Stage-worker entrypoint.** Add `src/core/orchestrator/worker-main.ts` (new) as the systemd entrypoint for the stage-worker service. It constructs db, executor, queue, and starts the BullMQ worker that consumes `stage-runs` jobs by calling `executeStageRun`.
- **BullMQ job config.** Jobs configured with `removeOnComplete: true` (avoid Redis bloat), `attempts: 3, backoff: { type: 'exponential', delay: 2000 }` (BullMQ native redelivery on worker crash — see D1-resolution), `lockDuration: 300_000` (5 minutes, accommodates long-running stages without premature lock expiry mid-execution).

### Systemd units + install script (NEW)

**GTM-portability rule.** Service unit files use `__FLUXAOS_REPO_PATH__` and `__FLUXAOS_ENV_PATH__` placeholders. The install script performs `sed` substitution at install time with absolute paths. No `%h`, no `$HOME`, no `$XDG_*`. This is per D2 — the only diff between user-level and system-level deployment is the install target path and an optional `User=` directive.

- `scripts/systemd/fluxaos-orchestrator.service` — unit file template for the orchestrator process. `ExecStart=/usr/bin/env npx tsx src/core/orchestrator/main.ts` (matching existing script conventions). `WorkingDirectory=__FLUXAOS_REPO_PATH__`, `EnvironmentFile=__FLUXAOS_ENV_PATH__` (both substituted at install time to absolute paths). `Restart=always`, `RestartSec=2s`, `StandardOutput=journal`, `StandardError=journal`. `WantedBy=default.target`.

Idempotent. At GTM, the install target changes to `/etc/systemd/system/` and the script writes unit files with `User=fluxaos` added; no other code changes.

### Gate-evaluation idempotency — v3 update

Previously R-UI-2 relied on `hasGateBeenEvaluated(stageRunId)` as the sole idempotency guard before gate evaluation. v2 review confirmed this is a read-then-write TOCTOU race, not cross-instance safe.

**Correct fix:** A partial unique index on `event(stage_run_id)` filtered to `type = 'gate_checked'`. The DB enforces exactly-once; `appendEvent(EVENT_TYPE.gate_checked, ...)` wrapped in try/catch treats a unique-violation as "already handled" and returns cleanly. `hasGateBeenEvaluated` remains as a cheap pre-flight check to avoid the DB round-trip on the happy path, but the index is the real atomicity guarantee.

## Exit criteria

Direct, verifiable, user-visible. No "the code compiles" language. These overlap deliberately with R5-V's exit criteria (which were never met); R-UI-2 closes that gap.

1. **Stream output arrives line-by-line.** Trigger a pipeline run. Lines appear in `LiveOutput` as they are produced, not in a batch at completion. Visible in Raw JSON mode too — no "all events appear at end" symptom. (Verified against `stage-runner.ts:299-317` — event inserts are already per-line via `runService.appendEvent` in the `onStdout` / `onStderr` callbacks, NOT buffered. Switching the client from `eventsQuery.refetch()` to `setData` append is therefore sufficient; no server-side write-cadence change required.)
2. **Activity feed auto-refreshes.** Open an issue's detail page in two browser tabs. Trigger a pipeline from tab A. Tab B's activity feed updates without being reloaded.
3. **Duration ticks.** Open `RunDetailModal` for an active run. The "Duration" label in the header increments every second without a user interaction.
4. **Adapter boundary is clean.** `grep -r "@supabase/supabase-js" src/` returns matches only in `src/adapters/supabase/`, `src/lib/supabase/`, and `src/core/db/` (where Drizzle itself imports type definitions). Zero matches in `src/core/`, `src/components/`, or `src/app/`.
5. **Gate-result rule rows show content.** The dots in `GateResultsPanel` render field/operator/value text instead of being empty.
6. **Orchestrator is running.** `systemctl --user status fluxaos-orchestrator` shows `active (running)` after install. `journalctl --user -u fluxaos-orchestrator` shows structured startup logs.
7. **Orchestrator recovers across restart.** With a pipeline run in `running` state, run `systemctl --user restart fluxaos-orchestrator`. On restart, the orchestrator logs show `recoverOnStartup` ran and stale `running` stage_runs are handled per D1 (BullMQ-tracked left alone, orphans re-queued or failed). No stuck-in-running rows remain.
8. **BullMQ absorbs stage-worker restarts.** Start a pipeline run. Gracefully restart the stage-worker mid-run (`systemctl --user restart fluxaos-stage-worker`). The graceful shutdown path closes the BullMQ worker cleanly, which returns the job lock to the queue; the revived worker picks up the job within seconds. The stage_run completes without manual intervention. **This is the durability test for the common-case restart scenario.** The SIGKILL-unclean-shutdown scenario is a separate, slower path gated on `lockDuration` (5 min by default); it is exercised only in manual testing, not in the Playwright suite, because a 5-minute journey test is impractical. R-UI-2's Playwright test therefore uses `systemctl --user restart` (clean) not `kill -SIGKILL` (unclean).
9. **Cancel works against a running stage.** Start a pipeline run, click Cancel in the modal while a stage is active. Stage transitions to `cancelled`, pipeline run transitions to `cancelled`, no further events emit. A subsequent orchestrator or worker restart does NOT re-launch the cancelled stage.
10. **Stage-worker and orchestrator are separate services.** `systemctl --user status fluxaos-stage-worker fluxaos-orchestrator` shows both `active (running)` after install. Killing one does not affect the other.
11. **Playwright journey suite still green.** The six `@r-ui-1` journeys continue to pass. Five new journeys under `@r-ui-2` tag pass: `live-output-streams`, `activity-feed-auto-refreshes`, `cancel-running-stage`, `orchestrator-recovers-after-restart`, `bullmq-requeues-on-worker-restart`.
12. **Integration tests green.** `orchestrator.test.ts` rewritten for event-orchestrator + BullMQ passes. Full `npx vitest run` is 0 failures.
13. **Human verification pass.** User walks the manual verification checklist end-to-end in a real browser. No self-certification.

## Resolved design decisions

Previously open questions, now decided:

### D1. BullMQ-backed dispatch for orchestrator crash recovery; subprocess re-attach deferred

**Context.** R5-V spec line 162 describes re-attaching to a still-alive subprocess if the orchestrator dies mid-stage. This is OS-level (`/proc/{pid}/fd/*`) and was not implemented in R5-V.

**Decision.** R-UI-2 wires the orchestrator's stage dispatch through the existing BullMQ queue adapter (`src/adapters/bullmq/queue.ts`) and `stage-worker.ts`. This gives the common case (orchestrator crashes cleanly, subprocess dies with it) automatic requeue-and-retry via BullMQ's built-in unacked-job recovery — the moral equivalent of Celery's task redelivery. A new orchestrator instance picks up the requeued job.

The rare case (orchestrator dies but the subprocess somehow survives with its pipe severed) is not handled by re-attach in this phase. Such a stage_run is marked `failed` on `recoverOnStartup()` with an explicit "orphaned subprocess" event. Re-attach is deferred to a future phase where the complexity is justified by the use case.

**Why this is principled, not lazy.** Frameworks at this tier (Celery, Sidekiq, BullMQ) universally re-run work rather than re-attach to it. That's because task semantics (idempotent operations that can safely re-run) are the design pattern; re-attach is an OS hack that most production systems don't use. We match the industry pattern.

### D2. User-level systemd for R-UI-2; GTM-safe by construction

**Context.** User-level (`systemctl --user`) avoids root requirements and matches the homelab dev environment. The concern is that switching to system-level at GTM must be a config change, not a rewrite.

**Decision.** Ship user-level service for R-UI-2. Enforce GTM-portability rules in the code so the switch is trivial:

- All paths configured via `.env`, never derived from `$HOME` / `$XDG_*` / `process.env.USER`.
- Temp workspaces go under `/tmp/fluxaos-runs/{stageRunId}/` (already R5-V spec — retain).
- No assumptions about user-level filesystem conventions (e.g. no writes under `~/.config`).
- Binds and listen addresses read from env, not hardcoded. The orchestrator itself doesn't listen on any socket for R-UI-2 scope, but if that changes the principle holds.
- Logs via stdout/stderr captured by `journalctl`. Works identically for user and system units — no code differences.
- The systemd unit file is a template: paths, user, and install target are parameterized via environment substitution. The only delta between user-level and system-level at GTM is copying the file to `/etc/systemd/system/` and adding `User=fluxaos` under `[Service]`.

### D3. Fold-in list confirmed; cosmetic deferrals remain deferred

**Context.** Whether GateResultsPanel fix, cancel verification, and orchestrator test rewrite should be in R-UI-2 or their own micro-phases.

**Decision.** Fold in. Each item is directly in R-UI-2's path:
- GateResultsPanel is a child component of `RunDetailModal`, which R-UI-2 is editing anyway.
- The cancel code path only becomes exercisable when the orchestrator is live — deferring cancel verification would defer R-UI-2's own exit criterion #8.
- `orchestrator.test.ts` targets code that transitions from "defined-but-unused" to "live" in this phase. Unskipping and rewriting it is the same unit of work as making the orchestrator real.

**Cosmetic deferrals (unchanged):** Text casing / verb tense inconsistencies, "Closed" vs "Complete" label, color mismatches — these remain in `deferred-fixes.md` and get their own future UI-polish pass. They are orthogonal to realtime, codebase-wide in character, and can be fixed without re-touching the realtime code. They fit the "minor fix that doesn't cascade" category.

**Non-cosmetic items folded in per this principle (i.e. things that would require re-touching R-UI-2 files later):** the three above. Anything else surfaced during implementation that would require re-opening R-UI-2 files later gets folded in at that point rather than deferred.

## Autonomy Contract

You run unattended. No human is watching. Do not ask. Do not wait. Do not pause for confirmation. The user may be asleep, away from the machine, or calling you from a script.

**Allowed exits per invocation:** completion, `state:on-hold`, or `state:failed`.

- **Completion** — work done, issue transitioned to the next pipeline stage, clean exit.
- **`state:on-hold`** — the current issue cannot proceed because work is required in another repository/system, credentials or external services are unavailable, or the user must make a product/architecture decision. File one issue per distinct blocker, link each as a blocker of the current issue, comment the reason, apply `state:on-hold`, exit cleanly.
- **`state:failed`** — you attempted the work and the implementation broke. Comment what broke, apply `state:failed`, exit.

**Agents own local blockers.** There is no separate development team. If the blocker is in this repository, the current workspace, the local toolchain, templates, tests, docs, or agent workflow, fix it or route around it autonomously. Do not use `state:on-hold` for work the user would normally tell an agent to do.

**On-hold is narrow.** Use `state:on-hold` only for:
- required changes in another repository or external system outside the current issue's ownership;
- unavailable credentials, secrets, accounts, devices, or external services;
- destructive or irreversible operations not already authorized by the user;
- genuine product or architecture decisions that require the user personally.

**Not on-hold.** Do not use `state:on-hold` for missing helper commands, local environment drift, failing tests, unclear but discoverable errors, merge conflicts, missing docs, missing fixtures, worktree setup issues, broken scripts, or agent/tooling friction. Diagnose and repair those first.

**Defaults are required, not optional.** Unless `--inline` is explicitly passed with a specific issue number, run delegated (subagent + worktree). If automatic delegation is unavailable, create or use an equivalent isolated local route when possible. Never silently fall back to unsafe inline execution, but do not stop if you can preserve the required safety property yourself.

**Blockers are tickets after remediation.** File blocker issues only after a concrete self-remediation attempt fails, or when the blocker meets the narrow on-hold criteria above. Two qualifying blockers = two issues. Three = three. Link all as blockers on the current issue, then `state:on-hold`.

**No silent degradation.** Do not downgrade required behavior because a capability seems unavailable. Preserve the requirement another way, fix the capability, or make the failure explicit. Use `state:on-hold` only when the narrow criteria apply; otherwise continue remediation or use `state:failed` if your attempted implementation broke.

**Never invent an external owner.** When instructions don't cover a case, assume the agents own it unless it meets the narrow on-hold criteria. The user is the only human decision-maker; do not defer to an imaginary team.

**Never apply `state:human-hold`.** That label is reserved for humans deferring work. Agents exit via `state:on-hold` or `state:failed`.

# Session Start
<!-- DO NOT EDIT this file directly. It is maintained by fhc sync and will be overwritten.
     Source: templates/skills/session-start/SKILL.md in fh-commons -->

Orient the current session without performing workspace cleanup.

## Usage

```bash
/session-start
/session-start --repo OWNER/REPO
/session-start --worktree <slug>     # Create and enter a new worktree before orienting
```

**Arguments:** `$ARGUMENTS`

## Step 0: Worktree Context

Determine the execution context:

```bash
WORKTREE_DIR=$(git rev-parse --show-toplevel)
MAIN_DIR=$(git worktree list | head -1 | awk '{print $1}')
if [ "$WORKTREE_DIR" != "$MAIN_DIR" ]; then
    echo "Running in worktree: $WORKTREE_DIR (slug: $(basename $WORKTREE_DIR | sed 's/.*-//'))"
else
    echo "Running in main checkout: $MAIN_DIR"
fi
```

If arguments include `--worktree <slug>` and the current directory is the main checkout, create and enter a new worktree:

```bash
 worktree create <slug>
# Then cd into the created worktree path before continuing
```

Skip this step if already in an isolated worktree.

## Step 1: Orient

Gather current work context:

```bash
git log -20 --oneline
 issue list --state open --limit 20
 pr list --state open
hippo memory list --category session --limit 5
```

Write a brief orientation summary. Include the current worktree context (from Step 0). Mention what's in flight, what's blocked or awaiting review, and the natural next action. If memory commands fail, skip the memory section and print a one-line warning.

## Step 2: Write Session-Start Marker

```bash
hippo memory add session "session-start" \
  --tags "session-start" \
  --body "Session started at $(date -Iseconds)"
```

If the command fails, print a warning and continue.

## Step 3: Ready Summary

One line:

```text
Session oriented. N issues open, N PRs open, N plans in flight.
Next likely action: invoke the pipeline skill matching the target issue's state label (see Step 4).
```

## Step 4: Hand Off to the Pipeline Skill

Before reading or modifying any issue, invoke the skill that matches the issue's `state:*` label:

| `state:*` label | Skill to invoke |
|-----------------|-----------------|
| `state:research` | `/research` |
| `state:ready-to-implement` or `state:implement` | `/implement` |
| `state:review` | `/review` |
| `state:rework` | `/rework` |
| `state:ready-to-deploy` | `/deploy` |

If no `state:*` label is present on the target issue, label it first:

```bash
 issue label <n> state:research
```

Then invoke the matching skill.

**Do not read the issue body or start any work before the matching skill is loaded.** The project's enforcement rules (tool-failure handling, filing discipline, verification requirements) live in the pipeline skill, not in training data. Skipping this step causes silent policy violations.
